# ADR-0005：官方曲库目录与账号

状态：采纳（v0.3.0）

## 背景

官方曲目太少。需要大量可合法使用的素材，让用户直接做单曲即兴重排；同时需要账号来同步收藏与最近使用。项目是 Apache-2.0 代码 + 学习研究定位，素材许可证来源复杂（CC0 / CC BY / CC BY-SA / CC BY-NC）。

## 决策

1. **素材与代码分离。** 素材不进 Git；以 `.upkit`（内含 FLAC）存放在数据服务，经 Worker 透传分发。每个条目带许可证 ID、作者署名、来源链接，随 Kit 元数据一起写入包内。
2. **四类来源**：现成开放分轨（`album`，如 AlbumDB CC BY 4.0）、在线曲库（`online`，如 ccMixter 按条目许可证）、MIDI + 开源音色库渲染的原创素材（`synth`，CC0）、用户导入后本地分轨并上传分享（`ugc`，上传与分享的后端已实现，本地分轨见第 9 项）。
3. **Kit 形态**：一首歌一个 Kit，**一个音色组（A/B/C…）= 歌曲的一个完整段落，组内一个 pad = 该段落的一个乐器分轨**，同组 pad 全开即完整放出这一段；各组 pad 序号与乐器一一对应，同一乐器跨组互斥，便于逐乐器换段落即兴。默认按小节量化，开箱即可玩。只有整曲混音时，在每段的空 pad 补 2 小节 / 1 小节片段。后续的用户导入自动拆分 Kit 沿用同一排布。（最初版本曾按乐器分组，已于 v0.3.0 发布后改为按段落分组。）
4. **许可证底线**：CC0、CC BY、CC BY-SA、CC BY-NC 都收，逐条标注。NC 条目使整体保持非商用定位；SA 条目的衍生 Kit 沿用同样许可证。导出录音若用了需署名的素材，在 WAV `bext` 元数据与分享文案里附署名。
5. **分发**：官网 Worker 提供目录 API，应用内按需下载；服务端存 FLAC，客户端入库时转 WAV（沿用 `up-library` 导入）。
6. **账号**：沿用 PlutoKeating 账号（`id.plutokeating.beer`，Ory Hydra）。App 客户端 `ultrapads-app`，授权码 + PKCE，使用 `flutter_appauth`。目录与下载匿名可用，登录后解锁云端收藏、最近使用、下载记录；日后的 UGC 上传也要求登录。
7. **后端**：延续 SayIt / J-nify 的模式——Cloudflare Worker（扩展现有 `website/worker`）只做验签、路由与透传，不处理字节；数据放深圳 ECS 上的 `ultrapads-data` 容器（SQLite + 本地文件），只对 Worker 开放。Worker 每请求 CPU 仅 10 ms，禁止在 Worker 里哈希或切分文件内容，完整性由 `sha256` 元数据让客户端核对。
8. **入库管线**：`tools/catalog` 脚本批处理（拉取、许可证校验、BPM / 小节对齐、切片、打包 `.upkit`、上传），发布前人工抽检；管线只写 `draft`，人工确认后改 `published`。
9. **UGC 上传与公开分享（已实现）**：登录用户把本地打好的 `.upkit`（≤ 128 MB，每账号 ≤ 50 条）上传到自己名下，上传时必须声明标题、署名、许可证（沿用白名单）和来源（`own` 自己的作品 / `licensed` 按所列许可证获得授权），**默认私有**；本人可改为公开，公开后进入目录（`origin: ugc`）。公开条目支持举报：同一用户只计一次，未处理举报累计 3 人自动隐藏待审，运营可恢复或下架（下架后 `410`）；注销账号连同上传一并删除。服务端只存储分发，不处理音频，Worker 对上传文件纯透传。契约见 `docs/API.md` §7.5。
    - **仍在后续期**：本地分轨（`Separator` trait，先 Demucs ONNX）。Demucs 预训练权重的授权存在争议，保持可插拔。

## 后果

- 新增运维面：`ultrapads-data` 容器、Kaiming 的 `ultrapads-app` 客户端、隧道的一条路径规则。运维细节记在对应私有仓库，不进本仓库。
- NC / SA 素材需要在 UI 与导出处给出提示，管线必须在入库时校验许可证。
- 目录内容随时可增删，不需要发版。
10. **本地分轨与导入歌曲拆分（已实现）**：`Separator` trait（`runtime/up-split`）+ Demucs（htdemucs 单文件 ONNX）后端，**纯 Rust 推理（tract）**，不引入原生运行时库，所以 Linux 与 Android 三个 ABI 的构建不变。导入歌曲的自动拆分沿用第 3 条的排布（一个音色组 = 一个完整段落，组内一个 pad = 一个乐器），接口见 `docs/API.md` §8。分轨在本机完成，云端不参与。
    - 模型不随应用分发：用户同意后从模型源下载，按固定 sha256 校验后存应用数据目录。权重授权在社区有争议（Demucs 仓库为 MIT，个别转换仓库标注非商业），选用明确标注 MIT 的 ONNX 导出，后端保持可插拔，以后可换 `ort` 等。
    - 取舍：tract 比 ONNX Runtime 慢、内存峰值约 4.6 GB（实测），所以按 `/proc/meminfo` 的可用内存决定是否开放分轨；内存不够的设备只提供不分轨的快速拆分（整曲混音，几秒）。实测 51 秒音频约 60 秒，分轨与原始分轨相关系数 0.97 以上。
